# 기차 구조 컴포지션 전환 설계 (상속 → 컴포넌트)

작성일: 2026-06-15
상태: **설계만 — 구현 미진행**

---

## Context / 문제의식

현재 기차는 **상속 구조**다: `Train`(베이스) → `TurretTrain` / `RangeTrain`.
"포탑이냐 범위냐"가 클래스 타입으로 굳어 있어 다음 문제가 있다:

- 새 공격 방식(예: 레이저 빔, 설치형 지뢰)을 추가하려면 **새 서브클래스 + 새 데이터 클래스 + 새 프리팹 컴포넌트**가 통째로 필요
- 능력/스킬/UI가 **구체 타입에 직접 캐스팅**(`Owner is TurretTrain` 등)해서 결합도가 높음
- 한 기차가 **두 공격 방식을 섞는 것**(예: 포탑 + 범위 둔화 장판)이 구조상 불가능

→ 목표: 공격 동작을 **컴포넌트(AttackModule)로 분리**해 하나의 `Train`에 붙이는 컴포지션 모델로 전환.
   배치/관리되는 동작 단위를 기차에 조립한다.

### 보존해야 할 진짜 동작 차이
| 측면 | TurretTrain | RangeTrain |
|---|---|---|
| 발사 모델 | 개별 투사체 버스트(다발/다중타겟, 풀링) | 지속형 범위 장판 1개(활성/비활성 토글) |
| 타이밍 | `FixedUpdate` 쿨다운 | `Update` 쿨다운 |

| 이벤트 | `OnAttacked(Monster)`, `OnTargetPosAttacked` | `OnAttacked()` |
| 고유 스탯 | `TargetCount` | `SlowRate` |

## 목표 아키텍처

```
Train (MonoBehaviour, 단일 클래스)
 ├─ HP / 레벨 / 사망 / 스킬모듈 / 스탯 베이스   (공통)
 └─ IAttackModule  (조립되는 공격 동작 컴포넌트)
       ├─ TurretAttackModule   : 개별 투사체 발사 + IProjectileEmitter
       ├─ RangeAttackModule    : 지속형 범위 장판
       └─ (확장) LaserAttackModule, MineAttackModule ...
```

- `Train`은 더 이상 `abstract`가 아니고 서브클래싱하지 않는다.
- 프리팹: 각 기차 프리팹에서 `TurretTrain`/`RangeTrain` 컴포넌트 → `Train` + `*AttackModule` 컴포넌트 조합으로 교체.
- 한 기차에 **여러 AttackModule**을 붙이면 복합 공격도 가능(향후).

### 공통 인터페이스 (결합도 제거의 핵심)

```csharp
// 패시브/스킬이 구체 타입 대신 이 인터페이스로 접근
public interface IAttackEvents
{
    event Action<Monster> OnAttacked;      // Range는 monster=null로 발행
    event Action OnTargetPosAttacked;      // 미지원 모듈은 미발행
}

public interface IExternalProjectileSpawner
{
    void SpawnExternalProjectile(Projectile prefab, float radius,
        IProjectileTarget target = null, float damageMul = 1f, float shoveScale = 1f);
}

public interface ITargetPosOverridable { Func<Vector3?> TargetPosOverride { get; set; } }
public interface IForceAttacker { bool ForceAttack(); }
// + 기존 IProjectileEmitter (Phase 1에서 도입 완료)
```

## 점진적 마이그레이션 (한 번에 갈아엎지 않음)

> 각 단계는 **독립적으로 머지 가능 + 동작 동일**해야 한다. 단계마다 에디터 컴파일/플레이 검증.

### Step 0 — 완료
투사체 모디파이어 파이프라인 + `IProjectileEmitter` (별도 브랜치 `dev/cumic/projectile-modifier-pipeline`).

### Step 1 — 인터페이스 추출로 타입 분기 제거 (상속 유지, 저위험) ✅ 구현 완료 (2026-06-15)
- 신규 `IAttackCapabilities.cs`: `IAttackEvents` / `IExternalProjectileSpawner` / `IForceAttacker`
  / `IShoveSuppressible` / `IProjectileAttacker`(포탑 고유 훅 묶음).
- `TurretTrain`이 `IAttackEvents, IProjectileAttacker, IExternalProjectileSpawner, IForceAttacker` 구현,
  `RangeTrain`이 `IAttackEvents, IExternalProjectileSpawner, IForceAttacker, IShoveSuppressible` 구현.
  - `RangeTrain.OnAttacked`를 `Action` → `Action<Monster>`(null 발행)로 통일.
  - `TurretTrain`에 `IExternalProjectileSpawner.SpawnExternalProjectile`(at-self 위임) 추가.
- **런타임 동작** 캐스팅 전부 인터페이스로 교체: 패시브 7개(FollowUp/PeriodicSpawn/Strengthen/
  RapidBombard/RepeatAfterAttack/ChainAttackChance/RandomPosBombard) + 스킬 2개(InstantAttack/Lightning).
- **남은 2곳**(`TriChoiceSelectUI.cs:196,219`)은 `TurretTrainStatus`/`RangeTrainStatus`(TargetCount vs
  SlowRate) 구조체·업그레이드 데이터 디스플레이라 **데이터 계층 문제 → Step 4로 이관**.
- **위험도 낮음** — 인터페이스 추가 + 캐스팅 교체뿐, 동작 변경 없음.
- ⚠️ 검증 한계: Unity 컴파일러 부재. 에디터에서 컴파일/플레이 확인 필요.

### Step 2 — 공격 로직을 AttackModule로 추출 (진행 중)
- `IAttackModule` 정의 (`Attack/IAttackModule.cs`): InitializeModule/스탯적용/업그레이드/진행도이관/Clear.
- **Step 2a ✅ RangeAttackModule 추출 완료 (2026-06-15)** — Range부터(프리팹 4개, 직렬화 0개 → 프리팹 수술 최소).
  - `RangeAttackModule : MonoBehaviour`가 공격 상태 + Update 루프 + 장판 투사체 + SFX +
    스탯 적용(범위 타입) + capability(IAttackEvents/IExternalProjectileSpawner/IForceAttacker/
    IShoveSuppressible/ISlowProvider)를 소유. 자체 Update로 공격 구동.
  - `RangeTrain`은 위임 shell: `GetComponent<RangeAttackModule>()` 후 Train 가상 메서드
    (Setup/Upgrade/StatusUpgrade/ApplyStat*/CopyProgressFrom/CurrentAttackRange/GetStatDetails 등)
    와 capability 인터페이스를 모듈로 forward. `OnAttacked`는 event add/remove 포워딩.
  - 동작 보존: Init radius 규약(Upgrade=AttackArea, 스탯=AttackRange) 등 원본 그대로 이관.
  - **에디터 마이그레이션 필수**: `TrainDefense/Migration/Add RangeAttackModule To Range Prefabs`
    메뉴 실행 → Range 프리팹에 모듈 컴포넌트 추가 → 프리팹 커밋. **실행 전엔 Range 기차가 공격 안 함.**
  - ⚠️ Unity 컴파일러 부재로 정적 검증만 수행. 에디터 컴파일 + 마이그레이션 + 플레이 확인 필요.
- **Step 2b ✅ TurretAttackModule 추출 완료 (2026-06-15)**
  - `TurretAttackModule : MonoBehaviour`가 공격 4종(Normal/Targeted/TargetPos/DirectDamage) +
    NonMovement 풀링 + 빔 스케일/파티클 정렬 + FixedUpdate 루프 + 스탯 적용 +
    capability(IProjectileEmitter/IAttackEvents/IProjectileAttacker/IExternalProjectileSpawner/IForceAttacker) 소유.
  - **직렬화 필드는 shell에 유지** (spawn points/turret/turretModel/flag) + 접근자(SpawnPoints/TurretObject/
    TurretModel/UseParticleProjectile/IsTargeting/IsRotateTurret) 노출 → 모듈이 읽음.
    → **프리팹 마이그레이션이 컴포넌트 추가만으로 끝남(필드 값 복사 불필요)**, Range와 동일하게 안전.
  - `TurretTrain`은 위임 shell: 업그레이드 부여 패시브 등록(_skillModule 소유)만 shell이 처리, 나머지는 모듈 위임.
  - `TrainBombardSkillAction`도 `is TurretTrain` → `IProjectileAttacker`로 정리.
  - 마이그레이션 메뉴를 `Add AttackModules To Train Prefabs`로 통합(Range+Turret 동시 처리).
  - ⚠️ Unity 컴파일러 부재로 정적 검증만 수행(치환 누락 0, brace 균형, 인터페이스 완전성, 외부참조 확인).
    에디터 컴파일 + 마이그레이션 실행 + 플레이 확인 필요. **마이그레이션 전엔 Turret 기차 미동작.**

### Step 3 — Train 단일화 + 프리팹 전환
- **Step 3a ✅ Train 비-abstract 호스트화 + 공통 위임 하이스팅 (2026-06-15)**
  - `Train`을 `abstract` 해제, `IAttackModule _attackModule` 보유(Setup에서 `GetComponent<IAttackModule>()` 연결).
  - 공통 위임을 Train으로 끌어올림: Setup(모듈 연결)/ApplyStat/ApplyStatsByCurrentValue/
    ApplyStatLevelAware/Upgrade/CopyProgressFrom/CurrentAttackRange/ClearAttachedProjectiles +
    공통 capability(IAttackEvents/IExternalProjectileSpawner/IForceAttacker) facade.
  - `TurretTrain`/`RangeTrain` shell 대폭 축소 → **타입 전용만 남김**: 직렬화 설정(turret),
    BaseStatus/StatusUpgrade(typed)/GetStatDetails(typed)/GetSkillSpawnPoint/ApplyPassiveSkills,
    포탑 전용 capability(IProjectileEmitter/IProjectileAttacker), 범위 전용(ISlowProvider/IShoveSuppressible).
  - **프리팹 변경 불필요** — 기존 "Add AttackModules" 마이그레이션이 그대로 충분(shell + 모듈 공존).
  - MainTrain(: Train, 모듈 없음)은 전 위임이 null-safe로 무동작 → 안전.
  - ⚠️ 정적 검증만(brace/abstract/중복impl/외부참조/MainTrain). 에디터 컴파일+플레이 필요.
- **Step 3b ⬜ shell 완전 제거 (선택, 고위험 — Unity 필수)**
  - 직렬화 설정(turret spawn points 등)을 shell → TurretAttackModule로 값 이전 +
    프리팹 컴포넌트 GUID를 TurretTrain/RangeTrain → Train으로 교체 + 베이스 직렬화 필드 복사.
  - 블라인드 자동 스크립트는 프리팹 손상 위험이 커 **에디터에서 백업 후 수동/반자동 진행 권장.**
  - 현 상태(3a)로도 컴포지션 목표는 달성 — shell은 얇은 타입 전용 클래스로 잔존(신규 공격타입은
    새 모듈 + 얇은 marker로 추가 가능, 또는 Train 직접 사용).

## 비용 / 리스크

- **총 추정**: 중대형 리팩터(스텝 합산 상당 규모). 핵심 난이도는 **패시브 이벤트 디커플링**과 **데이터/임포터 정리**.
- **가장 안전한 시작점은 Step 1** — 동작 그대로 두고 결합만 끊으므로 단독 머지 가능, 즉시 이득.
- Step 3(프리팹 일괄 교체)는 한 번에 36개를 건드리므로 **에디터 자동화 스크립트 + 시각 회귀 확인** 필수.
- 검증 한계: 이 환경에 Unity 컴파일러 없음 → 각 단계는 에디터에서 컴파일/플레이 확인 필요.

## 참고: 빌더 패턴은 어디에?

빌더와 컴포지션은 경쟁 관계가 아니라 **축이 다르다.**
- **컴포지션** = 무엇을 붙일까 (구조/확장성, 런타임 동작 교체) → 본 설계의 본질.
- **빌더** = 그걸 어떤 절차로 안전하게 조립할까 (생성 패턴).

이 프로젝트에서 빌더가 컴포지션을 대체하지는 못한다(Unity는 프리팹 `Instantiate` 기반이라
MonoBehaviour 생성자 빌더가 약하고, 이미 `TrainData`+`Initialize()`가 데이터 기반 빌더 역할).
다만 **Step 2~3에서 조립 절차가 다단계가 될 때 보조로** 유용하다:

```csharp
TrainAssembler.For(trainData)
    .WithAttackModule(...)        // 컴포지션 조립
    .WithSelectedSkill(skillType, id)
    .CopyProgressFrom(oldTrain)   // 엘리트 교체
    .Build();                     // MainTrain.SpawnTrain/ReplaceTrain 내부
```

→ 현재 `MainTrain.SpawnTrain`/`ReplaceTrain`에 흩어진 초기화 순서(생성→Initialize→
ApplyPassiveSkills→CopyProgressFrom→RestoreHp)를 한곳에 모을 때 도입 검토(필수 아님).
